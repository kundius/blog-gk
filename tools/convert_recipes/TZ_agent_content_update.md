# ТЗ: агент по обновлению содержимого статей

## 1. Цель

Создать отдельный чат с агентом, который выполняет обновление/правку содержимого
рецептов в БД. Агент работает в монorepo `blog-gk`, опирается на конвертер
`tools/convert_recipes/convert.py` и действует по тем же правилам, что и ручной прогон:
бэкап перед записью, транзакция, dry-run по умолчанию.

## 2. Стек и окружение

- Монorepo: `backend` (NestJS + Prisma), `site` (Next.js), `postgres`, `gateway` (nginx).
- Рабочий каталог внутри контейнеров `backend` и `site` — `/app`.
- На хосте есть `python3`, нет `node/npm/tsc`.
- Доступ к БД: `docker compose exec -T postgres psql -U blog_gk_user -d blog_gk_db`.
- Все команды — только из корня репозитория через `docker compose`.

## 3. Источники истины

- Исходник контента для переконвертации — `old_content` (если задан) либо `content`.
- Уже преобразованные статьи содержат `data-ingredients` (маркер «уже конвертированы»).
- `old_content` хранит оригинальный HTML, не трогается при `--apply` (кроме первого
  преобразования, где заполняется).

## 4. Требования к агенту

### 4.1. Безопасность данных
- **Бэкап перед любой записью.** Скрипт сам делает бэкап в
  `tools/convert_recipes/backups/pre_*.sql` (pg_dump). Агент обязан подтвердить наличие
  бэкапа до применения изменений.
- **Запись только через транзакцию** (в скрипте уже `BEGIN/COMMIT`).
- **Dry-run по умолчанию.** Агент не применяет изменения, пока пользователь явно не
  подтвердит запись.
- Не трогать `old_content`, кроме первого преобразования статьи.
- Не редактировать запрещённые зоны: `src/generated/`, `dist/`, `node_modules/`,
  `.next/`, `.env`, `.env.*`, существующие `backend/prisma/migrations/*`,
  `*.tsbuildinfo`, `*.pgsql`, `*.tar.gz`, `tools/migrate/*.sql`.

### 4.2. Процесс работы
1. Получить задачу от пользователя (какие статьи / какой тип правки).
2. Определить список id статей (явно, через `--ids-file`, либо выборка из БД по
   условию).
3. Выполнить dry-run и показать отчёт `STATS` + предупреждения `WARN`.
4. По запросу пользователя применить через `--apply`.
5. Прогнать валидацию до/после (см. §5) и показать результат.

### 4.3. Правила преобразования (наследуются из convert.py)
- Галереи создаются только внутри шагов `recipe-steps`.
- Подряд идущие изображения в шаге объединяются в одну `<div class="gallery">`.
- Текст-абзац между фото разрывает галерею (фото остаются раздельными).
- Герой/хвост статьи идут одиночными `<p><img>` (не галереи).
- Чинка битых `src` (удвоенное расширение `..jpg..jpg` -> `..jpg`) по
  `files.filename_disk`.
- «Сироты» (src без ведущего `/`, файла нет) — не чинить, только отчитываться.

## 5. Валидация результата

После применения агент обязан сверить:

| Метрика | Ожидание |
|---|---|
| Потери картинок | `gallery-image__img` и всех `<img>` — без изменений до/после |
| Подряд идущие галереи | `</div><div class="gallery">` -> 0 (если это цель правки) |
| Число затронутых статей | совпадает с выбранным списком |

Пример SQL-проверки (по конкретному списку id):
```sql
SELECT count(*),
       sum(regexp_count(content, 'gallery-image__img')) AS gimg,
       sum(regexp_count(content, '<img\s'))             AS allimg,
       sum(regexp_count(content, '<div class="gallery">')) AS blocks,
       sum(regexp_count(content, '</div><div class="gallery">')) AS consecutive
FROM articles WHERE id IN (...);
```

## 6. Ограничения и проверка кода

- Единственный инструмент проверки — `tsc --noEmit` в контейнерах
  (`backend`, `site`). ESLint/Prettier отсутствуют.
- Пользователь проводит поведенческое тестирование сам; агент не пишет unit/E2E-тесты.
- Если команда падает из-за особенностей окружения — не «чинить» более 1 раза,
  переходить к тайпчеку или логике.

## 7. Формат отчёта агенту-пользователю

- Показывать только `git diff`, не полные файлы.
- Пояснения — не более 2–3 предложений.
- Кратко: какие статьи затронуты, что изменено, метрики валидации, путь к бэкапу.

## 8. Запуск

```bash
# сухой прогон по конкретной статье
python3 tools/convert_recipes/convert.py <id> --force

# прогон по списку
python3 tools/convert_recipes/convert.py --ids-file ids.txt --force

# применение
python3 tools/convert_recipes/convert.py --ids-file ids.txt --force --apply
```
